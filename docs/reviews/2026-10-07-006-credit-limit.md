# Credit limit

Date: October 7, 2026
Status: Approved 2026-10-07
PR:

## Increment

A connected account now stores the credit limit the bank returns. A revolving debt that follows that account uses the limit. The person can keep their own instead. A loan, or a card whose bank did not send a usable limit, keeps the limit the person entered. Utilization uses the limit that is actually in use.

## Decision

The existing account sync copies `balances.limit` onto `Account.CreditLimit`. When the bank omits the limit, a previously stored one is cleared. Zero, a negative amount, and an amount over $100,000,000 are not usable. The debt then keeps the person's limit and does not label it as an override.

Only a revolving debt follows a usable limit. The latest snapshot date is that limit's as-of date, because that sync wrote it. The amount stored on the debt stays put until the person stops following. Stopping copies the synced limit when they had not set their own.

Setting the person's limit is `PUT /api/debts/{id}/overrides/CreditLimit`. Clearing it is the existing delete for that field. An amount equal to the synced limit is still an override. The card says "Your value since" the day they set it, shows the synced limit, and offers "Use synced limit". The balance button stays "Use synced value", so the two controls name the field. The form uses "Enter my own limit" and "Save my limit" for the same reason.

The confirm step names the credit limit when the account has one. When the person's limit differs, "Keep mine as my own value" saves that limit as an override, and a differing balance in the same step. A blank limit is not a difference. "Use this balance" on a reference link still starts a follow and uses the connected limit.

The form locks a followed limit until the person chooses to enter their own. A limit the connection did not provide stays editable, and saving the debt writes it. That save is not an override.

The person's stored limit has no date of its own, so the confirm comparison does not say the date is unknown. The connected side shows the snapshot date when there is one.

## Changes

- `Account.CreditLimit` and `Debt.CreditLimitOverriddenAt`. `DebtSyncedField.CreditLimit`.
- `DebtFollowedCreditLimit` resolves the limit in use. Follow, stop, and save use it. Utilization and the missing-limit count use the limit in use.
- The debt card, the edit form, and the follow confirm step show a synced limit and its override.

## Data changes

The model is updated. The migration is not generated.

After approval, these commands add a nullable `CreditLimit` on `Accounts` (`numeric(18,2)`) and a nullable `CreditLimitOverriddenAt` on `Debts`. Existing rows stay null. No existing follow becomes an override.

```powershell
dotnet ef migrations add AddAccountCreditLimit --project .\api --startup-project .\api
dotnet ef database update --project .\api --startup-project .\api
```

A followed card uses the bank limit only after a sync stores one. Until then the person's limit stays in use. Following can set `CreditLimitOverriddenAt`. Stopping can copy the synced limit onto the debt. A sync can change `Account.CreditLimit`. Account balances are not changed by the debt actions.
